# Probe와 worker 선택 실험을 위한 benchmark 검토

이 보고서는 다음 실험에 사용할 benchmark를 비교한다. 공식 논문·저장소의 작업 구성과 기존 GAIA 실험 분석을 근거로 추천한다. 후보 환경을 직접 설치하거나 새 모델 실행을 수행한 결과는 아니다. 추천은 연구 목적에 대한 적합성 판단이며, 성능 개선을 보장하지 않는다.

**현재는 MoNaCo와 WideSearch를 우선 검토하고, FanOutQA를 실행·평가 연결을 확인하는 pilot 후보로 둔다.** MoNaCo는 중간 정답과 근거를 이용해 worker 선택과 실패 원인을 분석하기 좋고, WideSearch는 많은 항목을 끝까지 조사하는 전체 시스템을 평가하기 좋다. LongCoT-Math는 수학에서 선택 가설을 확인하는 별도 후보다. **AppWorld는 바로 채택하지 않고, 실제 분해 가능성과 환경 이식 부담을 확인한 뒤 결정한다.**

이전 보고서는 AppWorld를 전체 시스템의 첫 후보로 권했지만, 작업 길이만으로 충분한 위임이 생긴다고 볼 수 없고 현재 도구와 다른 환경을 연결해야 한다는 부담을 충분히 반영하지 못했다. 이번 검토에서는 기존 웹 QA 도구를 재사용할 수 있는 후보를 추가하고 추천을 수정했다. 논문·공식 문서 확인 기준일은 2026-10-11(KST)이다. MoNaCo는 접근 동의가 필요한 원자료 전체를 직접 검사하지 않았으며, 논문·공식 데이터 설명·저장소에 근거해 판단했다.

## 1. 무엇을 확인하려는가

우리 시스템에서는 orchestrator가 다음 작업을 정하고 worker에게 위임한다. 실제 실행을 맡은 worker를 executor라고 부른다. Refiner는 실행 전에 위임 내용을 검토한다. Probe는 이때 worker에게 지시를 어떻게 이해했고 어떤 가정과 방법으로 실행할지 실제로 묻는 절차다. 사용자의 의도를 확인하는 질문과는 다르다.

이번 benchmark 선택에는 두 가지 연구 질문이 있다.

| 연구 질문 | 비교하려는 것 | 필요한 작업 특성 |
|---|---|---|
| 기존 probe 연구 | 실제 worker 응답을 받아 지시·전달 정보를 개선하는 것이 자체 검토나 probe 없는 실행보다 유용한가? | 실행 전에 확인할 해석·가정·도구 사용 문제가 있고, 개선된 지시나 정보가 실행에 영향을 줄 수 있어야 함 |
| 일관성 기반 worker 선택 | 첫 subtask를 반복해서 풀었을 때 일관된 답을 내는 worker가 이후 작업도 더 잘하는가? | 비교 가능한 첫 결과와 충분한 후속 작업이 있어야 함. 첫 작업이 지나치게 쉽거나 전체 문제의 대부분이면 부적합 |

새 선택 실험은 같은 첫 subtask를 후보 worker 각각에게 표현만 조금 바꿔 여러 번 맡기고, 결과가 가장 일관된 worker에게 나머지 작업을 맡기는 방식이다. 이는 기존 probe와 별개의 방법이다. 표현을 바꾸더라도 요구사항과 정답은 유지해야 한다.

추가로 검토 중인 전체 구성에는 공유 작업 기록, 필요한 정보의 선택·전달, 실행 전후의 evaluator가 포함된다. 공유 작업 기록에는 질문 해석, 가정, 확인한 사실과 근거, 완료·미완료 작업을 저장하고, 각 worker에게는 해당 작업에 필요한 항목을 전달한다. 앱의 데이터베이스처럼 실행으로 바뀌는 환경 상태와는 구분한다. 이 기능들을 함께 시험하려면 여러 단계에서 정보를 얻고 다시 사용하는 작업이 필요하다. 구체적인 구성은 [설계안](../design/shared-state-evaluation-and-routing.ko.md)을 참고한다.

## 2. 기존 실험에서 가져갈 판단 기준

GAIA 탐색 실험에서는 위임이 한 번뿐인 문제가 많았고, 추가 위임도 새로운 subtask보다 재확인인 경우가 있었다. 이 결과는 현재 시스템의 실행 방식에 관한 관측이지, GAIA를 원래 분해할 수 없다는 증거는 아니다.

Probe에서는 유효한 단서를 찾고도 전달하지 않거나, 원 질문보다 엄격한 조건을 추가해 답 후보를 배제한 사례가 있었다. 따라서 다음 실험은 응답을 많이 수집하는 것뿐 아니라 **얻은 정보를 보존하고 적절하게 사용하는지** 확인해야 한다. 핵심 47문제 비교에는 자체 검토 조건이 없었으므로, 실제 probe 응답의 고유 가치는 아직 판단할 수 없다. [기존 종합 분석](2026-10-10-synthesis.ko.md)

Benchmark의 한계를 다음 세 가지로 구분한다. 이 구분 없이 “안 맞는다”고 하면 연구 가설의 문제와 구현 부담을 혼동하기 쉽다.

| 한계의 종류 | 뜻 | 예시 |
|---|---|---|
| **실험 목적과의 적합성** | 확인하려는 현상이 작업에서 충분히 발생하는가 | 명확한 수학 지시에서는 해석 확인 probe가 재진술에 그칠 수 있음. 후속 작업이 거의 없으면 worker 선택 가설을 시험하기 어려움 |
| **효과 측정의 어려움** | 효과가 있어도 비교·채점으로 구분할 수 있는가 | 첫 답을 고른 효과와 이후 worker 능력이 섞임. 정답률이 거의 0 또는 100%여서 차이를 보기 어려움 |
| **구현·실행 비용** | 실험을 연결하고 반복하는 데 무엇이 필요한가 | 앱 환경 복제, 브라우저 인스턴스, 긴 실행, 별도 judge 비용 |

“해석 확인 기회가 적다”는 것은 그 benchmark에서 기존 probe를 시험하기 어렵다는 판단이지, probe가 모든 작업에서 무의미하다는 결론은 아니다. 반대로 해석 차이가 많다는 사실도 probe의 이득을 보장하지 않는다. 불필요한 조건 강화와 잘못된 수정도 함께 측정해야 한다.

Benchmark는 다음 기준으로 판단한다.

- **작업 구성:** 클릭이나 API 호출 횟수와 별개로, 의미 있는 subtask가 충분히 남는가?
- **Probe 기회:** 실제 worker에게 물어봐야 알 수 있는 해석·실행상의 차이가 있는가?
- **선택 신호:** 첫 결과를 비교할 수 있고, 그 작업이 이후에 필요한 능력과 관련되는가?
- **평가와 기록:** 최종 성공을 판정하고, 정보 누락·잘못된 수정·실행 오류를 구분할 수 있는가?
- **실행 부담:** 환경 구축과 반복 실행 비용이 연구 목적에 비해 감당할 만한가?

## 3. 후보 비교

아래 추천은 우리 연구 목적과 현재 도구를 기준으로 한다. 구현 부담은 필요한 작업에 대한 판단이며, 실제 개발 시간이나 실행 비용을 측정한 순위는 아니다.

| Benchmark | 작업과 주된 장점 | 기존 probe 연구 | 일관성 기반 선택 | 주된 한계·권장 위치 |
|---|---|---|---|---|
| **MoNaCo** | 여러 문서·표의 사실을 조회·집계; 중간 정답·근거 제공 | 해석과 정보 전달 오류를 단계별로 분석 가능 | 반복 조회와 후속 정답을 비교하기 좋음 | 첫 작업의 대표성·정답 시점·실행 연결 확인. 우선 검토 |
| **WideSearch** | 많은 항목을 조사해 표 완성; 행·항목별 평가 | 범위·열 해석과 누락 관리 확인 | 비슷한 조사 묶음 사이의 선택 실험 가능 | 중간 분해는 우리가 구성. 웹 실행 비용과 엄격한 완전 성공률에 주의. 우선 검토 |
| **FanOutQA** | Wikipedia 다중 문서 QA; 분해·평가 도구 제공 | 대상·근거 전달을 확인할 수 있음 | 충분한 후속 조회가 있는 문제를 선별 | 큰 작업이 모든 문제에 보장되지는 않음. pilot 후보 |
| **LongCoT-Math** | 답을 다음 문제에 사용하는 수학 묶음 | 명확한 지시에서는 해석 확인 기회가 적음 | 명시된 의존관계와 수학 답 비교가 장점 | 중간 정답 공개 범위·노드별 실행 연결 확인. 선택 가설의 별도 후보 |
| **AppWorld** | 여러 앱을 API로 조회·변경 | 실행 조건·정보 전달을 함께 시험 가능 | 실제 분해가 충분한 경우에만 유효 | 환경 격리·상태 연결 구현 부담. 적합성 확인 후 채택 |
| **WorkArena++** | 브라우저로 복합 업무 수행 | 절차 제공·검색 조건의 차이를 분석 가능 | 첫 조회가 후속 업무를 대표하는지 확인 필요 | 브라우저·환경 비용과 낮은 성공률 가능성. 후순위 |
| **ProgramBench** | 프로그램을 처음부터 재구현 | 가정·설계·구현 전달을 시험 가능 | 첫 기능과 전체 개발 능력이 다를 수 있음 | 긴 실행과 구현 동치성 평가 부담. 후순위 |
| **OOLONG-synth** | 문서 분류·필터링·집계 | 해석 확인보다 누락·집계 관리에 적합 | 비슷한 문서 묶음으로 구성 가능 | 쉬운 분류만으로는 선택 차이가 없을 수 있음. 보조 실험 |
| **ParallelQA** | 소수의 검색 후 계산 | 전달 연결 점검에 적합 | 후속 작업이 적고 첫 조회가 쉬울 수 있음 | 연구 효과보다 실행 연결의 초기 점검 |
| **ARC-AGI-2** | 예시에서 grid 변환 규칙 추론 | 규칙 검토는 가능 | 첫 규칙 발견이 전체 풀이에 가까움 | 후속 worker 능력 검증과 거리가 있음. 후순위 |
| **IMO-ProofBench** | 엄밀한 수학 증명 작성 | 증명 계획 검토는 가능 | 서로 다른 올바른 풀이의 일관성 비교가 어려움 | 별도 증명 평가 설계 필요. 후순위 |
| **GAIA** | 웹·파일·이미지·계산 QA | 기존 probe 오류의 회귀 점검에 적합 | 현재 실행에서는 남는 작업이 적음 | 기존 사례 유지; 새 선택 실험의 주 환경은 아님 |

### MoNaCo — 중간 정답으로 선택 효과와 실패 원인 분석

**설명.** 사람이 작성한 1,315개 질문에 답하기 위해 여러 Wikipedia 문서와 표의 정보를 조회·필터링·집계한다. 근거 페이지는 질문당 평균 43.3개, 중앙값 12개다. 논리적 분해 단계는 평균 5.1개이고, 각 대상에 대해 구체화한 중간 질문은 평균 66.5개, 중앙값 23개다. 수십 질문이 모두 순차 단계라는 뜻은 아니며, 독립 조회와 결과에 의존하는 집계가 함께 있다. [공식 논문](https://aclanthology.org/2026.tacl-1.2.pdf)

**우리 실험에 맞는 이유.** 분해 단계, 중간 질문·정답, 이전 단계의 입력값, 근거 URL·문장·섹션·표의 열을 제공한다. 첫 일관성과 나머지 정답률의 관계를 분석하고, 최종 실패가 조회·전달·집계 중 어디에서 발생했는지 확인할 수 있다. 대상 범위·기준 시점·표의 열에 대한 이해가 worker 사이에서 달라지는지도 probe와 공유 작업 기록으로 추적할 수 있다. 이러한 해석 차이는 실제 실행에서 확인해야 할 가설이며, 데이터에 assumption conflict가 정답으로 주석되어 있다는 뜻은 아니다. [공식 데이터 설명](https://huggingface.co/datasets/allenai/MoNaCo_Benchmark)

**맞지 않을 수 있는 이유.** 대상 목록을 만드는 첫 작업과 대상별 속성을 조회하는 후속 작업은 다른 능력을 요구할 수 있다. 첫 목록의 일관성이 이후 정확도를 예측하지 못해도 선택 방법 전체가 무효라고 단정할 수 없다. 같은 유형의 조회 사이에서도 효과가 없는지 구분해야 한다. 또한 중간 질문이 많아도 worker 하나가 묶어서 처리할 수 있으므로 실제 위임 수는 별도 확인한다. 이는 비용보다 실험 가설과 작업 구성의 문제다.

**평가·비용상의 제약.** 약 절반의 질문은 시간에 따라 정답이 바뀔 수 있다. 공식 평가는 LLM judge를 사용하며, 논문의 대표 성능은 주로 도구 없는 설정에서 나온 결과다. 현재 웹 agent의 예상 성공률로 해석하지 않는다. 첫 pilot은 시간에 덜 민감한 질문을 사용하고, judge 설정을 고정해 일부 판정을 수동 점검한다. [논문 평가·한계](https://aclanthology.org/2026.tacl-1.2.pdf)

원자료 접근에는 동의가 필요하고, 확인한 공식 저장소는 웹사이트·prompt 중심으로 README에 코드가 “Coming soon”으로 표시되어 있다. 데이터 로딩, 단계별 실행, 채점 연결을 확인해야 한다. 현재 웹 도구를 재사용할 여지는 있지만 준비된 multi-agent 실행 환경으로 간주하지 않는다. [공식 저장소](https://github.com/tomerwolgithub/monaco)

**권장 사용.** 선택 실험은 정답을 숨긴 고정 subtask로 시작한다. 같은 유형의 첫 조회와 후속 조회를 비교한 뒤, 첫 단계에서 다른 유형의 후속 작업으로 선택 효과가 이어지는지도 본다. 전체 시스템 실험에서는 원래 질문만 주고 orchestrator가 분해하도록 한다. 정답 분해는 사후 분석에 사용하며 유일한 올바른 계획으로 취급하지 않는다.

### WideSearch — 많은 항목을 끝까지 조사하는 전체 시스템

**설명.** 영어·중국어 각 100개, 총 200개 과제에서 다수의 사실을 수집해 표로 정리한다. 완전 성공률뿐 아니라 행 단위 F1과 항목 단위 F1을 제공한다. F1은 제출한 결과의 정확성과 정답을 빠짐없이 찾은 정도를 함께 평가하며, 행 단위는 완성된 레코드, 항목 단위는 개별 셀을 비교한다. 채점에는 규칙 검사와 의미 비교용 LLM judge가 함께 쓰인다. [공식 설명·평가](https://widesearch-seed.github.io/)

**우리 실험에 맞는 이유.** 같은 포함 기준과 열 정의를 여러 대상에 적용하므로, worker에게 전달한 해석이 일관되는지와 조사한 항목을 빠짐없이 합쳤는지 확인하기 좋다. 첫 조사 묶음과 후속 묶음이 비슷한 일을 하도록 구성하면 선택 신호의 대표성을 높일 수 있다. 현재 웹 검색·페이지 읽기 도구를 재사용할 수 있어 앱 환경을 새로 연결하는 것보다 구현 범위가 작을 것으로 예상한다.

**맞지 않을 수 있는 이유.** 주된 어려움이 해석보다 검색량·완전성이라면, 해석 확인 probe를 늘려도 개선되지 않을 수 있다. 이때 probe가 의미 없는지 판단하려면 실제 해석 오류가 얼마나 있었는지 먼저 봐야 한다. 또한 정답 표의 행·항목을 채점할 수 있다는 것과 정답 분해·중간 trace가 제공된다는 것은 다르다. 선택용 subtask는 우리가 구성하고, 이미 답을 알고 분할한 덕분에 쉬워진 결과와 자율 분해 결과를 구분한다.

**평가·비용상의 제약.** 공식 보고에서는 모든 항목을 맞혀야 하는 완전 성공률이 매우 낮았다. 그것만 보면 개선이 가려질 수 있으므로 행·항목 F1과 누락을 함께 본다. 많은 검색을 후보마다 반복하는 선택 실험은 비용이 커질 수 있다. 구현 부담이 작다고 실행 비용도 작다고 간주하지 않는다. [논문](https://arxiv.org/abs/2508.07999)

### FanOutQA — 선택 실험의 실행 경로를 확인할 pilot

**설명.** Wikipedia에 기반한 다중 문서 QA로, 1,034개 질문과 사람이 작성한 7,305개 분해 질문 및 답을 포함한다. 대상들을 찾은 뒤 각각의 정보를 조사하는 fan-out 구성을 다룬다. [공식 논문](https://aclanthology.org/2024.acl-short.2.pdf)

**우리 실험에 맞는 이유.** 개발 데이터의 분해·중간 답과 공식 로딩·평가 도구를 이용해 선택용 반복, 후속 실행, 채점을 연결할 수 있다. 검색·페이지 읽기 도구와도 가깝다. 문서 참조에는 Wikipedia revision 정보가 포함되어 정답의 기준 문서를 추적할 수 있다. [공식 API](https://fanoutqa.com/api_reference.html)

**맞지 않을 수 있는 이유.** 각 문제에 선택 후 충분한 조회가 남는지는 확인해야 한다. 분해가 짧거나 첫 단계가 대부분의 답을 결정하면 GAIA에서 본 문제가 반복될 수 있다. 첫 대상 목록과 후속 조회의 유형 차이도 남는다. 해석 확인 probe의 효과를 기대하려면 대상·근거 해석이나 실행 방법의 차이가 실제 오류와 연결되는지 확인해야 한다.

**평가·비용상의 제약.** 개발 데이터와 테스트 데이터의 공개 범위가 다르므로, 개발용 중간 주석을 테스트에도 쓸 수 있다고 가정하지 않는다. 공식 평가에는 여러 지표와 추가 의존성이 있어 우리가 사용할 지표·judge·설치 범위를 먼저 정해야 한다. pilot을 구성하기 좋다는 판단이지 MoNaCo보다 실행 비용이 낮다는 실측 결과는 아니다. [공식 실행 안내](https://fanoutqa.com/index.html)

### AppWorld — 실제 분해와 환경 이식을 확인한 뒤 채택

**설명.** 9개 앱과 457개 API로 구성된 환경에서 수행하는 750개 작업이다. 에이전트는 코드를 작성해 정보를 조회하고 조건에 따라 작업을 수행한다. 평가는 최종 데이터 상태를 검사해 목표 달성과 불필요한 변경을 확인한다. [공식 논문](https://arxiv.org/abs/2407.18901)

**추천 이유.** 실행 전에는 대상 선정 기준, API 사용 방법, 필요한 정보 등을 확인할 수 있다. 실행 중에는 얻은 대상 ID·조건·조회 결과와 완료 항목을 다음 worker에게 전달해야 한다. 따라서 기존 probe, context list, executor 선택, evaluator를 연결해 시험할 여지가 있다. 프로그램 전체를 새로 만드는 것보다 앱 안의 업무를 수행하는 환경이므로 기존 도구 사용 연구와도 연결하기 좋다.

**실험 적합성의 한계.** 복잡한 앱 작업도 coding worker 하나가 코드로 한 번에 처리할 수 있다. 의미 있는 후속 위임이 남는지 확인하기 전에는 전체 시스템의 주 benchmark로 채택하지 않는다. 첫 로그인이나 문서 조회의 일관성은 이후 작업 능력을 잘 나타내지 못할 수 있다. 개발용 작업에서 첫 대상 집합의 조회·필터링·분류처럼 비교 가능한 subtask가 있는지 먼저 확인한다. API 호출 수를 subtask 수로 세지 않는다. 서로 다른 코드가 같은 결과를 만들 수 있으므로 코드 문자열보다 조회 결과와 실제 변경 내용을 비교한다.

**구현·평가 부담.** 현재 웹·파일 중심 실행에 앱 API, 인증·대상 ID 전달, 변경 가능한 데이터 상태를 연결해야 한다. Probe와 후보별 반복을 격리하려면 파일 작업 공간뿐 아니라 앱 데이터도 초기화·복제해야 한다. 환경 checkpoint와 우리 실행 재개의 연결도 확인해야 한다. 이 때문에 후순위로 두는 것이지, probe 기회가 없다고 판단한 것은 아니다. 현재 모델에서 normal이 너무 쉽거나 challenge도 너무 어려운지는 개발 표본의 성공률로 확인한다. 과거 모델의 성공률만으로 천장·바닥 효과를 확정하지 않는다.

공식 환경은 실행 입출력, API 호출, 데이터 변경 기록과 상태 checkpoint를 지원한다. 같은 조건에서 반복 실험하고 trace를 분석하는 데 유리하다. 환경을 복원하는 기능은 실험 조건을 맞추는 용도와 agent에게 재시도 능력을 주는 용도를 구분해야 한다. 개발·오류 분석에는 train/dev를 사용하고, 최종 평가용 작업의 정답·평가 내용을 실행 모델에 제공하지 않는다. [공식 환경·평가 안내](https://github.com/StonyBrookNLP/appworld)

### WorkArena++ — 업무 절차 이해와 브라우저 실행

**설명.** ServiceNow 업무 시스템에서 브라우저로 수행하는 복합 작업이다. 같은 341개 업무를 L2와 L3로 제시해 총 682개 과제를 구성한다. L2는 상세한 절차를 제공하고, L3는 ticket에 목표와 정보를 주며 필요한 절차를 knowledge base에서 찾게 한다. 재고 확인 후 주문하고 ticket을 종료하는 작업 등이 있다. [공식 논문 §3](https://arxiv.org/html/2407.05291v1)

**추천 이유.** 절차가 명시된 경우와 직접 찾아 구성해야 하는 경우에서 probe의 효과를 비교할 수 있다. 찾아낸 업무 규칙, 대상 레코드, 수집한 값과 완료한 절차를 기록·전달할 필요도 크다. 작업 구성 자체가 여러 작은 업무의 결합이어서 전체 진행 상황을 관리하는 실험에 적합하다.

**실험 적합성·평가의 한계.** L2에서 이미 상세 절차가 주어지면 해석 확인 probe가 추가할 정보가 적을 수 있다. L3에서는 정보를 찾을 기회가 늘지만, 이득이 해석 확인 때문인지 사전 검색 때문인지 구분해야 한다. L2와 L3는 지시의 명확성뿐 아니라 검색·기억 부담도 다르므로, 효과 차이를 해석 개선 하나로 설명하면 안 된다. 첫 클릭의 성공은 이후 업무 능력을 대표하지 않을 수 있다. 의미 있는 조회·판단 결과를 첫 subtask로 잡고, 화면 탐색 실패와 업무 이해 실패를 구분한다. 논문의 당시 최고 agent 성공률은 L2 약 4%, L3 0%였다. 현재 모델에서도 낮다면 조건 간 차이를 보기 어려우므로 개발 표본으로 먼저 확인한다. 이는 probe의 무효를 뜻하지 않고 평가의 바닥 효과 가능성이다. [당시 평가 결과](https://arxiv.org/html/2407.05291v1)

**구현 부담.** 브라우저 executor와 원격 환경이 필요하며, 현재 설치 절차에는 ServiceNow 인스턴스 접근과 BrowserGym·Playwright 설정이 포함된다. [공식 설치 안내](https://github.com/ServiceNow/WorkArena)

### LongCoT-Math — 일관성 기반 worker 선택

**설명.** LongCoT는 짧은 입력에서 여러 단계의 긴 추론을 요구하는 benchmark다. 수학 분야에는 앞 문제의 답이 뒤 문제의 조건이 되는 Linear·DAG 유형과 조건 분기·역방향 탐색 유형이 있다. [공식 논문](https://arxiv.org/html/2604.14140v1)

**추천 이유.** 수학 subtask와 의존관계가 명시되어 있고 숫자·분수 등의 답을 비교할 수 있다. 첫 subtask를 반복해서 풀게 하고 선택한 worker에게 나머지를 맡기는 실험을 비교적 직접 구성할 수 있다. 쉬운 문제로 구성된 LongCoT-Mini의 Linear 유형부터 확인하고 DAG로 넓히는 것을 권한다. 공식 코드는 분야·난이도별 로딩과 최종 답 검증을 지원한다. [공식 코드](https://github.com/LongHorizonReasoning/longcot)

**한계와 사용 방법.** 첫 답이 틀리면 이후에도 오류가 전파된다. 성능이 올라도 첫 답을 잘 고른 효과인지, 이후에 잘할 worker를 고른 효과인지 구분해야 한다. 별도 비교에서 모든 worker에게 같은 첫 결과를 제공하면 후자의 예측력을 확인하기 쉽다. 수학 분야가 단계마다 달라질 수도 있으므로 첫 문제의 대표성은 보장되지 않는다.

**기존 probe와의 적합성.** 요구사항이 명확해 기존 probe가 단순 재진술이나 사전 풀이가 될 가능성도 있다. 따라서 기존 probe 연구 전체의 주 benchmark로 삼기보다 선택 가설을 확인하는 데 사용한다. 우리 multi-agent 실행 결과는 단일 모델·도구 없는 공식 주 설정과 구분해서 보고한다.

**연결·평가 확인 사항.** 공식 입력은 여러 노드를 한 prompt에 제시한다. 노드별로 실행·전달하는 방식은 우리가 추가해야 하며, 전체 정답 검증 기능만으로 각 노드 정답까지 공개되어 있다고 판단하지 않는다. 중간 정답의 공개 범위와 노드 분리 가능성을 확인한 뒤 채택한다. 큰 외부 환경이 없다는 장점은 있지만, 긴 풀이와 반복 실행의 비용은 별도 측정한다.

### ProgramBench — 긴 프로그램 개발 과정

**설명.** 실행 파일과 문서만 주고 같은 동작을 하는 프로그램을 처음부터 구현하게 하는 200개 작업이다. 구조와 구현 방법은 agent가 결정하고, 평가는 원본과 제출 프로그램의 동작을 비교한다. [공식 설명](https://programbench.com/)

**추천 이유.** 기능 조사·설계·구현·수정이 이어져 후속 작업이 충분하다. Probe가 확인한 동작과 가정을 보존하고, worker 간에 설계 결정과 완료 기능을 전달하며, evaluator가 구현 결과를 검토하는 실험에 적합하다.

**실험 적합성과 비용의 한계.** Probe가 가정을 확인할 여지는 충분하지만, 첫 기능을 안정적으로 구현하는 능력이 전체 설계 능력을 대표하지 않을 수 있다. 긴 개발을 후보마다 반복하면 선택 비용도 크다. 따라서 후순위 이유는 probe의 무의미함보다 실행 부담과 선택 신호의 대표성이다. 서로 다른 유효한 구현 계획을 충돌로 취급해서도 안 된다. 일관성은 코드가 아니라 동일 입력에 대한 동작으로 비교한다. 최종 평가용 테스트는 선택이나 풀이에 제공하지 않는다. 전체 해결 여부와 테스트 통과율을 함께 보고, Linux x86_64 Docker 환경과 개발 실행 예산을 별도로 준비해야 한다. [공식 실행·평가 안내](https://github.com/facebookresearch/ProgramBench/blob/main/docs/README.md)

### OOLONG-synth — 반복 분류와 집계

**설명.** 많은 짧은 문서를 분류한 뒤 개수, 사용자별 분포, 시간별 변화에 관한 질문에 답한다. OOLONG-real은 실제 대화 자료를 사용하며, 문서를 독립 항목으로 나누기 더 어렵다. [공식 소개](https://oolongbench.github.io/)

**추천 이유.** 문서들을 여러 묶음으로 나누면 첫 묶음과 후속 묶음이 비슷한 능력을 요구한다. 항목별 결과와 완료 범위를 기록하고 누락·중복을 검사하기 쉬워 context list와 집계 평가의 보조 실험에 적합하다. 이런 묶음 단위 실행은 우리가 추가하는 방식이다.

**한계와 사용 방법.** 논문은 개별 분류보다 정보 식별과 집계를 주요 어려움으로 분석한다. 첫 묶음의 분류만 비교하면 모든 worker가 일관되게 맞혀 선택할 차이가 없을 수 있다. 첫 subtask에도 최종 질문과 관련된 조건 필터링·부분 집계를 포함하되, 분할 과정에서 필요한 사용자·시간 정보를 잃지 않아야 한다. 명확한 분류 기준이 주어진다면 기존 probe가 해석 확인으로 더할 정보는 적을 수 있다. 이는 환경 비용보다 기존 probe와의 적합성 문제다. 분류·집계 계획 확인까지 probe의 범위를 넓히면 별도 연구 조건으로 보고한다. [논문 §4.5](https://arxiv.org/html/2511.02817v1)

### ParallelQA — 간단한 작업 의존관계

**설명.** 여기서는 LLMCompiler 논문의 ParallelQA를 뜻한다. 113개 질문에서 여러 대상의 정보를 검색하고 그 결과로 계산한다. 최대 병렬 작업 수를 2~5개로 구성했고, 필요한 정보를 Wikipedia 첫 문단에서 찾을 수 있도록 설계했다. [논문 §5.2·Appendix I](https://www.stat.berkeley.edu/~mmahoney/pubs/icml2024_kim24y.pdf)

**추천 이유.** 검색 결과가 어떤 계산의 입력이 되는지 분명하다. 작업 위임과 결과 전달이 정상적으로 연결되는지 초기 점검하기 좋다.

**한계.** 작업 규모가 작고 첫 검색이 쉬울 수 있어 첫 subtask의 일관성으로 이후 성능을 예측하는 주 실험에는 약하다. 이는 주로 후속 작업량과 선택 신호의 문제이며, 큰 환경 구축 비용 때문은 아니다. Probe도 간단한 검색 지시를 재진술하는 데 그칠 수 있다. 웹 자료가 바뀌는 영향도 고려해야 한다.

### ARC-AGI-2 — 예시에서 grid 변환 규칙 찾기

**설명.** 입력·출력 grid 예시를 보고 규칙을 추론해 새 입력의 출력 grid를 만든다. 보통 시범 예시는 3쌍, 테스트는 1~2개다. [공식 데이터 설명](https://github.com/arcprize/ARC-AGI-2/blob/main/readme.md)

**검토 이유와 한계.** 출력 grid를 정확하게 비교할 수 있어 후보 풀이 선택에는 적합하다. 그러나 첫 의미 있는 작업이 변환 규칙 발견이라면 전체 문제를 상당 부분 해결한 셈이다. 여러 후속 subtask에 걸친 worker 능력을 보려면 별도의 변형이 필요하므로 이번 연구에서는 후순위다. 도구 환경 비용보다 실험 목적과의 거리 때문에 미룬다. 규칙 검토 probe 자체가 불가능하다는 뜻은 아니다.

### IMO-ProofBench — 엄밀한 수학 증명

**설명.** 60개 수학 문제에 대해 증명을 작성한다. 기준 증명과 채점 지침을 제공하며 자동 채점도 지원한다. 별도로 Lean 4 형식 증명을 위한 IMO-LeanProofBench가 있다. [공식 설명](https://imobench.github.io/)

**검토 이유와 한계.** 긴 추론과 증명 검토를 연구할 수 있지만, 서로 다른 올바른 증명과 보조정리를 같은 결과로 판정하기 어렵다. 첫 단계의 일관성을 평가하는 모델의 품질이 실험에 크게 개입할 수 있다. Lean은 증명을 기계적으로 검증할 수 있으나 환경 연결과 실험 설계가 추가로 필요하다. 증명 계획을 확인하는 probe는 가능하지만, 답의 일관성 정의와 채점 부담 때문에 단순한 선택 방식의 첫 실험으로는 권하지 않는다.

### GAIA — 기존 실패 경로의 회귀 점검

**설명.** 웹 검색, 파일·이미지 판독, 계산 등을 결합하는 질의응답 benchmark이며 현재 프로젝트가 사용한 환경이다.

**유지 이유.** 출처·시점·대상 범위·집계 단위의 해석과 자료 접근 문제가 결합되어 기존 probe 연구와 관련성이 높다. 우리가 발견한 정보 전달 누락, 불필요한 조건 강화, 후속 재확인의 문제를 다시 확인할 수 있다. [기존 사례와 종합 분석](2026-10-10-synthesis.ko.md)

**한계와 사용 방법.** 기존 probe가 확인할 해석·실행 차이는 있지만, 현재 실행에서는 첫 위임 이후에 충분한 독립 작업이 남지 않는 경우가 많아 새 worker 선택 실험의 주 환경으로는 약하다. 기존에 분석한 문제는 회귀 점검용으로 사용하고, 일반화 성능은 별도의 미열람 평가 문제에서 확인한다. 과거 prompt의 관측을 현재 구성의 성능으로 간주하지 않는다.

## 4. 권장하는 실험 범위

**먼저 MoNaCo·WideSearch의 작은 표본에서 적합성을 확인하고, 실행 연결을 빠르게 점검할 필요가 있으면 FanOutQA를 사용한다.** 세 환경의 전체 평가를 동시에 구축하자는 뜻은 아니다. 중간 오류 분석이 중요하면 MoNaCo를, 많은 항목의 완성과 취합이 중요하면 WideSearch를 먼저 연결한다. LongCoT-Math는 수학 선택 가설을 따로 확인할 때 사용한다. AppWorld는 아래 확인과 환경 이식 범위 추정을 거친 뒤 채택한다.

채택 전에는 원래 질문만 주는 실행에서 다음을 확인한다.

- **의미 있는 후속 작업:** 첫 선택 이후 독립적으로 수행하거나 결과를 전달할 작업이 얼마나 남는가? 재확인·클릭·API 호출을 새 subtask로 세지 않는다. 위임이 세 번 이상인지 같은 수치도 참고할 수 있지만 개수만으로 채택하지 않는다.
- **모델 간 차이와 난이도:** 현재 후보들이 모두 맞히거나 모두 틀리는가? 첫 일관성이 서로 다른가? 정답률이 너무 낮으면 부분 점수와 실패 위치로 개선을 관측할 수 있는가?
- **Probe가 확인할 내용:** 실제로 해석·가정·실행 방법의 차이가 있는가? 차이가 없으면 probe가 불필요한지, 질문이 정보를 끌어내지 못했는지 구분해 기록한다.
- **필요한 구현과 비용:** 도구 adapter, 격리·초기화, 채점, trace 연결 중 무엇을 새로 만들어야 하는가? 소수 실행의 토큰·도구 호출·시간을 측정해 선택 비용까지 예상한다.

기존 GAIA 사례는 회귀 점검용으로 유지한다. 기존 지시 수정에서 관찰한 조건 강화·답 보류·해석 확정은 benchmark를 바꿔도 재발할 수 있다. 이를 점검하면서 새 benchmark의 연결을 진행한다. 현재 refiner를 통합한 결과만 보고 probe의 효과를 해석하지 않는다.

실험은 두 경로로 구분한다. **선택 가설 확인에서는 subtask를 고정**해 첫 일관성과 후속 정확도의 관계를 본다. **전체 시스템 평가에서는 orchestrator가 분해**하고 probe·공유 작업 기록·evaluator·executor 선택을 함께 붙인다. 먼저 전체 성능을 확인한 뒤 기능을 하나씩 제외하는 ablation으로 기여를 확인한다. 고정 분해에서 얻은 효과를 자율 분해에서도 그대로 기대하지 않는다.

선택 실험에서는 다음을 공통으로 지킨다.

- **답의 일관성과 정확도를 따로 측정한다.** 반복해서 같은 오답을 내는 worker도 있다. 수학 답은 동치인 수식, QA는 정규화한 대상·속성·목록, 앱 작업은 대상·값·변경 결과처럼 비교할 단위를 미리 정한다. 목록의 높은 일관성이 같은 누락을 반복한 결과일 수 있으므로 정답 대비 정확도·누락률도 따로 본다.
- **선택용 실행과 평가용 실행을 분리한다.** 각 고정 worker가 전체 문제를 독립적으로 반복 실행한 결과(초기안은 worker당 3회)와, 선택한 worker의 새로운 실행 결과를 비교한다. 고정 worker뿐 아니라 무작위 선택도 비교한다.
- **첫 결과의 전달 규칙을 맞춘다.** 선택 과정에서 얻은 답을 후속 실행에 넘기는지 명시한다. 첫 답의 개선과 이후 worker 능력을 구분하려면 같은 첫 결과를 준 비교를 추가한다.
- **초기 환경과 총예산을 기록한다.** 후보별 반복은 서로의 데이터 변경에 영향을 받지 않아야 한다. Probe·선택·재작성·평가 호출을 모두 비용에 포함하고, 비용을 맞춘 비교도 구분한다. 후보가 k개이고 후보당 첫 subtask를 n회 반복하면 선택에만 k×n회 풀이가 필요하다. 이 추가 비용을 후속 정확도 개선과 함께 보고한다. 실험 결과 채점 비용과 실제 시스템의 실행 중 evaluator 비용도 따로 기록한다.
- **실패를 발생 단계별로 확인한다.** 해석 오류, 잘못된 수정, 전달 누락, 실행 오류, 평가·종료 오류를 구분한다. 환경 로그, worker에게 실제로 전달한 정보, 공유 작업 기록의 변경 내용을 함께 남긴다.

실제 probe의 고유 가치를 보려면 자체 검토와의 비교가 필요하다. 정보를 미리 얻는 효과와 지시문을 바꾸는 효과도 다르다. 전체 구성 평가 뒤에는 실제 probe 제외, executor 고정, evaluator 제외 등의 비교를 수행하고, 필요하면 관측 정보만 전달하는 조건과 재작성만 하는 조건을 비교한다.

MoNaCo 등 중간 주석을 사용하는 경우 정답·근거·평가용 trace는 실행 모델에 제공하지 않는다. 같은 원 질문의 subtask를 개발·평가로 나누지 않고 원 질문 단위로 분리한다.

개발용 표본은 선택 기준과 실행 예산을 정하는 데 사용한다. 유의미한 정확도 차이를 검증할 본 평가의 표본 수는 그 변동성을 본 뒤 정하고, 같은 task의 조건별 차이와 불확실성을 함께 보고한다. 하나의 task 안에 subtask가 많다는 이유로 독립 평가 표본 수가 늘었다고 계산하지 않는다.
