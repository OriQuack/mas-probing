# 851e570a — Boggle 최장 단어 (gold Briniest)

## 4.1 과제와 의도된 풀이

- 보드 ABRL / EITE / IONS / FPEI, 8방향 인접·셀 재사용 금지(Boggle 규칙), 사전은 dwyl/english-words의 `words_alpha.txt`로 고정. 최장 단어, 동률이면 알파벳 순 첫 단어.
- Annotator: 사전을 내려받아 Python trie+DFS로 전수 탐색 → 8글자 'briniest', 'brionies', 'inertiae', 'pointrel' 중 알파벳 첫 단어 "Briniest". (GAIA scorer는 대소문자를 정규화하므로 "BRINIEST"도 정답.)
- 이 시스템에서의 핵심 제약: `run_python`은 "no network"(tool 목록에 명시)라서 사전을 Python에 올릴 수 없다. 사전은 3,864,813자(약 37만 항목, `read_url_text` 194페이지)다. 접근 수단은 (a) `read_url`: page reader LLM이 약 25만 자 단위 ~16개 part를 각각 읽음 — 한 번에 5-12분, (b) `read_url_text`: 194페이지(호출 한도 20회로 불가), (c) `find_in_url`: 정확 문자열 검색, 1초 미만.
- 실패 지점 후보: 전수 검증이 불가능한 도구 환경에서 "exhaustive" 검증을 반복하다 wall-clock 예산(3600 s)을 소진하는 것.

## 4.4 Pre-execution preventability — d0 instruction이 runaway와 실패를 막을 수 있었나

**Runaway(시간 소진)에 대해: 일부 완화 가능 (MAYBE-KNOWHOW, 사전에 알 수 있음).**
- 검토자는 실행 전에 tool 목록에서 `run_python`이 network가 없다는 것을 알 수 있고, `words_alpha.txt`가 수백만 자(약 37만 단어) 규모라는 것도 공개 정보다. 따라서 "사전을 Python에 올려 trie로 전수 탐색하라"(v6 draft)는 실행 불가능한 요구이며, `read_url` 전체 스캔은 비싸고 불안정하다는 것을 예견할 수 있다. `read_url`의 지연(1회 5-12분)은 문서화되어 있지 않아 정확한 비용은 알 수 없다.
- 완화 지시 예: "run_python has no network, so the full dictionary cannot be loaded for an exhaustive trie search. Use at most two read_url passes over words_alpha.txt to collect candidate words of 8 or more letters; check each candidate's board path in run_python and its exact membership with find_in_url (never use read_url for single-word membership). **실패(최종 답 부재)에 대해: d0로는 막기 어렵다 (NO).**
- 결정적 실패는 d0 이후 orchestrator의 재검증 결정이다. v5에서는 d0 report가 이미 확신에 찬 형태였는데도 "did not provide exhaustive-check details"를 이유로 재검증했으므로, d0 지시를 바꿔 report의 단서 문구를 없애도 재검증이 일어났을 가능성이 높다. 재검증 단계의 실행 방식은 d1 instruction(orchestrator 작성)이 정하고, v6 d1의 reader는 오히려 "BRINIEST ... not an entry"라고 잘못 말했다. d0가 빨라져 시간이 남았더라도 최종 답이 BRINIEST로 유지될지는 불확실하다.
