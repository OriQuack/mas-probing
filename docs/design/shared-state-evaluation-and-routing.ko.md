# Executor 선택, 작업 기록, probe·실행 평가 설계안

지금까지는 worker에게 보내는 지시문을 고쳤을 때의 효과를 알아보기 위해 실행 모델을 고정했다. 다음 실험에서는 **문제를 더 잘 푸는 전체 구성을 먼저 만들고, 이후 기능을 하나씩 제외하는 ablation으로 각 기능의 기여를 확인**하려 한다. 이 문서는 executor 선택, 기록·전달, probe와 실행 결과의 평가, 지시문 수정을 어떻게 연결할지 설명한다.

현재 runtime은 실행 `v13` / probe·refiner `r15` / evaluator `e3` / tools `v6`로 구현했다. 실제 모델의 개선 효과는 아직 평가하지 않았다. 아래 사례와 설계 동기는 도입 전 기록을 설명한다. 근거는 과거 실행을 재분석한 [종합 보고서](../reports/2026-10-10-synthesis.ko.md), 연결된 trace 분석, 그리고 [v10/r12의 30개 실행 기록](../../outputs/experiments/2026-10-11_v10-r12-check/)이다. 새 실행은 task·조건당 1회이므로 실패 경로를 확인하는 자료로 사용하며, 기능별 평균 효과를 입증한 것으로 보지 않는다.

## 1. Executor를 선택하도록 바꾸는 이유

Executor는 위임받은 작업을 실제로 실행하는 worker다. 기존에는 역할마다 executor 하나를 고정했고, 다른 worker는 주로 실행 전 질문인 probe에만 답했다. 고정한 이유는 실행 모델이 바뀌는 효과와 지시문 수정 효과를 섞지 않기 위해서였다.

이제는 전체 문제 해결 성능을 먼저 보려 하므로 executor를 고정할 필요가 줄었다. 다음 작업을 정하는 orchestrator가 그 작업을 맡길 worker도 선택하도록 한다. 선택에는 지원 도구와 입력 형식, 남은 예산, 모델 비용을 사용한다. 기존 실험으로 어느 worker가 더 잘 실행하는지 확인한 것은 아니므로, 선택 기능의 이득은 새 실험에서 확인해야 한다.

Probe와 실행은 수행하는 일이 다르므로 현재의 별도 prompt를 유지한다. Evaluator는 probe 응답과 실행 보고를 평가하고, refiner는 그 평가를 받아 선택된 worker에게 보낼 지시문을 다듬는다. 별도 delegator는 두지 않고 다음 작업 선택과 위임 초안 작성은 orchestrator가 맡는다.

## 2. 무엇을 저장하고, 무엇을 worker에게 전달할 것인가

### 현재 방식에서 어려운 점

지금은 orchestrator가 이전 보고를 읽고 다음 worker에게 필요한 정보를 `context`라는 문자열로 적는다. 여러 위임에 걸친 작업에서는 확인한 항목, 남은 항목, 적용한 가정, 판단을 바꾼 이유를 매번 이 문자열과 대화에서 찾아야 한다.

| 실제 사례 | 확인한 문제 또는 성공 경로 |
|---|---|
| [arXiv](../reports/cases/analysis/a7feb290.md) | 성공 실행은 확인한 논문 구간·ID·부분합과 미확인 항목을 계속 기록했다. 실패 실행에는 일부 항목을 확인하지 못한 채 끝낸 경우가 있었다 |
| [OpenCV](../reports/cases/analysis/56137764.md) | worker가 버전 전체의 기여자와 특정 기능의 구현자를 구분해 보고했지만, orchestrator는 수정 지시의 좁아진 기준으로 답 후보를 배제했다 |
| [Ruffwear](../reports/cases/analysis/_allcorrect.md) | probe가 이미지에서 브랜드 단서를 찾았지만 refiner는 이를 전달하지 않고 날짜 조건을 강화했다 |

arXiv는 작업 진행을 기록할 필요를 보여준다. OpenCV는 기록된 정보를 해석하고 사용하는 규칙도 필요하다는 사례다. Ruffwear는 probe에서 얻은 정보를 지시문 수정 여부와 별개로 전달할 필요를 보여준다.

다만 arXiv의 성공 실행은 자유 텍스트로도 기록을 잘 유지했다. OpenCV에서는 필요한 구분이 이미 보고에 있었다. 따라서 목록을 도입하면 반드시 좋아진다는 증거는 아니다. 다음 설계는 이런 기록과 전달을 매번 자유롭게 작성하는 대신 같은 방식으로 관리하려는 제안이다.

### Artifact pool, state, context의 차이

`context`는 기존 코드의 뜻을 유지한다. **이번 worker에게 원 질문·지시문과 함께 보내는 이전 정보**다. 모델 입력 전체를 가리키는 일반적인 뜻의 context와는 구분한다. `state`는 한 문제를 푸는 동안 유지하는 **현재 진행 상황과 판단**을 뜻한다. Context는 별도 공유 저장소가 아니라 위임마다 구성하는 입력이다.

| 구분 | 담는 내용 | 실제 사용 |
|---|---|---|
| Artifact pool | probe 응답, 실행 보고, 평가와 재사용할 자료·파일 등 원본 기록. ID·제목·worker・단계를 연결 | 요약의 근거가 필요하면 해당 ID로 원문을 읽음. 논문의 memory pool에 해당 |
| State | 확인한 결과, 적용 중인 가정과 근거, 남은 작업, 시도한 탐색, 서로 맞지 않는 주장 | Orchestrator가 다음 작업과 executor를 선택하고, evaluator가 판단을 검토하며 refiner가 수정할 내용을 파악하는 데 사용 |
| Context | 이번 작업에 필요한 이전 결과·가정·출처를 선택해 담은 내용 | 해당 worker 호출에 실제로 전달. 위임마다 필요한 내용이 달라짐 |

Artifact pool의 원본은 보존하고, state는 평가와 결정에 따라 갱신한다. Context는 이들 중 이번 작업에 필요한 내용을 골라 만든다. 원 질문과 이번 지시문은 context와 별도로 제공한다.

### 실제 사용 예시: 논문 97개의 특정 형식 제공 여부 세기

아래는 arXiv 사례를 바탕으로 기록과 전달의 차이를 보여주는 예시다. 특정 정답이나 항목별 판정을 실제 prompt에 미리 넣는다는 뜻은 아니다.

이미 1–30번 논문을 확인했고 다음 worker에게 31–50번을 맡긴다고 하자.

| 위치 | 들어갈 내용 |
|---|---|
| 원본 기록 `m1` | 전체 97개 논문의 목록과 출처 |
| 원본 기록 `m2` | 형식 제공 여부를 어떻게 판단했는지, 확인한 페이지와 비교 결과 |
| 원본 기록 `m3` | 1–30번의 항목별 판정과 근거를 담은 실행 보고 |
| State | 대상은 97개, 현재 판정 기준의 근거는 `m2`, 1–30번은 확인했고 31–97번은 남아 있음. 확인하지 못한 예외가 있으면 따로 기록 |
| 다음 instruction | 31–50번을 확인하고, 항목별 판정·근거·확인하지 못한 항목을 보고하라 |
| 다음 context | `m1` 중 31–50번 ID, `m2`의 판정 방법과 근거, 이 구간과 관련된 예외 |

Orchestrator는 **state를 보고 다음 구간을 고른다.** Probe가 그 지시를 어떻게 이해했는지 답하면 evaluator가 가정과 근거를 검토한다. Refiner는 평가에서 필요한 것으로 판단한 변경을 instruction·context에 반영한다. Worker는 **선택된 context를 받아 그 구간을 실행한다.** 전체 과거 보고를 받을 필요는 없다. 이후 evaluator가 새 실행 보고를 검토하고 state의 완료 범위와 미확인 항목을 갱신하도록 제안한다.

### 목록과 읽기·쓰기 방식

Artifact pool에는 원본 조회와 출처 확인에 필요한 다섯 항목만 둔다. 논문의 ID·제목·본문 구조에 worker 선택과 probe·실행 구분에 필요한 자동 metadata를 더한다.

| Column | 작성 주체 | 의미 |
|---|---|---|
| `id` | Harness | 원본 조회용 고유 ID |
| `worker_id` | Harness | 생성한 worker 또는 평가 모델의 ID |
| `stage` | Harness | probe·실행·평가 등 생성 단계 |
| `title` | 생성 모델 | 본문을 열기 전에 내용을 파악할 수 있는 짧은 제목 |
| `body` | Harness가 응답 저장 | 응답 전문 또는 재사용할 자료·파일의 내용과 참조 |

지원 도구·입력 형식·비용은 별도 worker 목록에서 제공한다. Artifact의 worker_id는 결과의 출처를 알려주며, 그것만으로 해당 worker가 더 잘한다고 판단하지 않는다. 호출 ID 등 상세 metadata는 기존 trace에 남긴다. 도구 결과는 원문을 trace에 보존하되 모든 호출을 artifact 목록에 올리지 않고, 재사용할 중요한 자료·파일을 연결한다. 모델 응답이 아닌 자료는 harness가 원래 호출의 worker·단계와 제목을 붙인다.

State는 다음 판단과 작업에 영향을 주는 항목을 네 column으로 관리한다.

| Column | 의미 |
|---|---|
| `type` | 관측 / 가정·해석 / 결과 / 진행 |
| `content` | 현재 주장 또는 작업. 필요한 조건·대상·시점도 문장 안에 명시 |
| `status` | 관측·가정·결과는 미확인 / 지지됨 / 기각됨, 진행은 미완료 / 완료 / 막힘 |
| `refs` | 판단의 근거가 되는 artifact ID |

“지지됨”은 그 내용에 근거가 있다는 뜻이지 절대적인 확정을 뜻하지 않는다. Artifact를 인용했다는 이유만으로 가정을 확인된 사실로 올리지 않는다. Worker의 understanding은 그 worker의 해석이며, probe의 plan은 완료한 작업이 아니다. 조건부 결과가 지지된 것과 그 조건 자체가 지지된 것도 구분한다.

아래는 실제 Secret Santa trace를 바탕으로, 첫 실행 보고까지 받은 시점을 표현한 예시다. ID와 제목은 설명용이다. 새 evaluator의 판정을 실제 실행 결과로 제시하는 것은 아니다.

| Artifact ID | Worker | 단계 | 제목 |
|---|---|---|---|
| a1 | Haiku의 worker ID | probe | 표 방향에 대한 두 가지 해석 |
| a2 | 해당 executor의 worker ID | 실행 | Fred가 유력하지만 방향은 미확정이라는 보고 |

| 종류 | 내용 | 상태 | 근거 |
|---|---|---|---|
| 관측 | 표 머리글은 Giftee와 Recipient다 | 지지됨 | a1 |
| 가정·해석 | 두 번째 열을 받는 사람으로 읽는다 | 미확인 | a1, a2 |
| 가정·해석 | 방향을 명시적으로 증명하지 못하면 답을 보류해야 한다 | 미확인 | a1, a2 |
| 결과 | 두 번째 열을 받는 사람으로 읽으면 답 후보는 Fred다 | 지지됨 | a2 |
| 진행 | 첨부 표를 읽고 해당 해석에 따른 후보를 도출했다 | 완료 | a2 |
| 진행 | 표와 이야기 문맥을 비교해 해석을 평가한다 | 미완료 | a1, a2 |

별도 state ID나 conflict column은 우선 두지 않는다. 충돌은 어떤 주장들이 왜 맞지 않는지 content에 적고 관련 artifact를 참조한다. OpenCV의 “버전 기여자는 Li Peng”과 “기능 구현자는 dkurt”는 다른 대상을 말하므로 양립할 수 있다. 검토할 것은 “답 후보가 기능 구현자여야 한다”는 추가 조건이 원 질문에 맞는지다.

읽기·쓰기는 다음처럼 나눈다.

1. **Harness가 원본을 저장한다.** Harness는 모델 호출과 도구 실행을 관리하는 코드다. 새 응답에 ID·worker_id·stage를 붙이며, probe 정보도 지시문 수정 여부와 관계없이 저장한다. 평가와 결정 원문도 이력에 남긴다.
2. **모델은 필요한 기록을 읽는다.** Orchestrator·refiner·evaluator는 목록에서 ID를 골라 `read_memory(ids)` 같은 도구로 본문을 읽는다. 과거 본문 전체를 매번 입력에 붙이지 않는다. Evaluator에게는 이번에 새로 나온 보고 전문을 직접 제공한다.
3. **Evaluator가 state 변경을 제안한다.** Probe 이후에는 관측·가정·위험과 필요한 확인을, 실행 이후에는 결과·완료 범위·탐색 이력을 평가한다. Refiner는 state를 별도로 판정하거나 덮어쓰지 않는다.
4. **Harness가 변경을 기록하고 orchestrator가 중요한 판단을 결정한다.** 원본 연결과 미확인 가정·시도 이력은 평가 결과에 따라 기록한다. 기존 결과를 뒤집거나 원 질문의 답 기준을 바꾸는 제안은 orchestrator가 근거를 보고 채택 여부를 결정한다. Harness는 참조 ID와 변경 이력을 관리하며, 참조 검사를 내용의 진실성 검사로 취급하지 않는다. 평가를 따르지 않을 때도 이유를 남긴다.
5. **Refiner가 필요한 수정만 반영한다.** 원 질문, 위임 초안·context, 관련 state와 평가 결과를 받는다. 해결되지 않은 판단을 임의로 확정하지 않는다. 수정이 필요 없으면 rewrite 호출을 생략할 수 있다.
6. **Harness가 context를 구성해 worker에게 보낸다.** Orchestrator가 artifact ID와 필요한 state 항목을 선택하면 harness가 실제 내용·출처·확인 상태로 구성한다. Refiner는 전달 내용의 누락이나 표현을 보완할 수 있지만, context 수정으로 state의 판단을 바꾸지 않는다. 새 판단이 필요하면 evaluator에 재검토를 요청한다. Worker가 조회 도구 없이 ID만 받는 상황을 만들지 않는다.

Context는 별도 저장소나 read/write 대상이 아니다. Artifact pool은 ID로 읽고, state는 evaluator의 갱신 제안을 harness가 반영한다. 실제 전달한 context는 위임별 trace에 저장한다.

여러 모델이 같은 기록을 직접 덮어쓰게 하지 않는다. 원본은 남기고, 현재 판단을 변경할 때 이전 판단과 변경 근거를 보존한다. 원 질문에 맞지 않는 기존 해석도 수정할 수 있어야 한다.

실패한 탐색도 별도 schema 대신 state의 진행 항목으로 적는다. 탐색 이력은 “못 찾음”만 남기지 않는다. 시도한 검색어·자료, 검색 결과·초록·본문 중 읽은 범위, 접근 차단인지 내용 불일치인지, 다음 시도에서 달라지는 단서를 기록한다. v10/r12의 Freud baseline은 미완료 탐색을 반복했으므로 “완료한 작업을 반복하지 말라”만으로는 막기 어렵다. 다만 다른 실행은 탐색을 이어가 본문을 찾아 성공했으므로, 같은 미완료 작업이라는 이유만으로 재시도를 금지하지 않는다.

### 기대하는 변화와 한계

확인한 항목을 다시 맡기거나 미확인 항목을 빠뜨리는 일을 줄이고, 어떤 가정 때문에 결과를 채택·배제했는지 따라가기 쉽게 만드는 것이 목적이다. Probe가 발견한 출처나 단서도 instruction을 고치지 않은 경우에 전달할 수 있게 한다. 현재는 수정할 issue가 없으면 이를 추가하는 rewrite 단계도 건너뛴다. [현재 refiner 코드](../../src/minpilot/refine/review.py).

반대로 잘못 작성한 state가 이후 모든 판단에 반복될 수 있고, 목록과 본문 조회의 비용도 늘 수 있다. 그래서 원문으로 돌아갈 수 있는 ID를 유지하고, 새 보고라는 이유만으로 이전 결과를 바꾸지 않는다. 효과는 최종 정답률·비용과 실제 전달 누락·중복 확인을 함께 보고 판단한다.

## 3. Probe와 실행 결과를 evaluator가 평가하는 이유와 방법

### 왜 필요한가

현재 refiner 파이프라인은 probe를 수집한 뒤 analysis에서 문제와 해결 방식을 판단하고 rewrite에서 지시문을 고친다. 새 설계는 **기존 analysis의 판단을 evaluator로 옮기고 refiner는 필요한 수정에 집중**하도록 한다. 초기 probe 질문은 현재처럼 코드가 고정된 prompt에 위임 초안을 넣어 만든다. 추가 질문이나 사전 확인이 필요하면 evaluator가 제안하고, 코드는 정해진 예산 안에서 호출한다.

v10/r12 실행에서는 probe의 우려를 analysis가 받아들인 뒤, rewrite가 이를 답 기준으로 반영하는 실패가 있었다.

| 새 실행 사례 | 평가 단계에서 구분해야 할 내용 |
|---|---|
| arXiv `a7feb290` | 현재 format 페이지가 과거 상태를 입증하지 못한다는 우려와, 모든 항목에 당시 증거를 필수로 요구한다는 결정은 다르다. 두 probe 조건 모두 analysis가 clarify로 처리했으므로 defer_to_execution 문구만 고쳐서는 부족하다 |
| Secret Santa `cffe0e32` | 표 머리글은 관측이다. 명시적으로 방향을 증명하지 못하면 답을 보류해야 한다는 것은 추가 판단이다 |
| USDA `676e5e31` | 항목명 대응에 관한 probe의 질문을 제외 규칙으로 확정했다. 이름과 포함 기준을 어떻게 해석할지 평가하기 전에 실행 조건으로 만들었다 |

이 기록은 수정 전에 probe 응답의 근거와 의미를 평가할 필요를 보여준다. 별도 evaluator가 더 정확하다는 증거는 아니다. 같은 모델이 기존 analysis를 그대로 반복하면 역할 이름만 바뀐다. 원 질문을 좁히는 판단 규칙도 함께 고쳐야 한다.

실행 후에는 현재 orchestrator가 보고를 평가하면서 다음 작업과 종료까지 결정한다. 이 평가도 evaluator가 맡아 결과와 근거를 먼저 검토한다. 과거 trace에서도 다음 문제가 있었다.

| 과거 사례 | 검토해야 했던 내용 |
|---|---|
| [ORCID](../reports/cases/analysis/bec74516.md) | 일부 저자의 pre-2020 논문 수가 전체 논문 수보다 큰데 그대로 평균을 계산해 제출했다. 집계의 중복과 부분집합≤전체를 확인할 수 있었음 |
| [Freud](../reports/cases/analysis/65638e28.md) | worker는 Feuerbach를 답으로 볼 근거가 없다고 보고했지만 orchestrator가 최종 답으로 선택했다. 보고와 최종 선택이 맞지 않았음 |
| [USDA](../reports/cases/analysis/676e5e31.md) | 6/7을 구한 뒤 amendment를 제외하는 기준으로 재확인하여 결과가 바뀌었다. 그 변경이 원 질문과 출처에서 정당화되는지 검토할 필요가 있었음 |

이 사례들은 평가할 문제가 있음을 보여주지만 개선 효과를 입증하지는 않는다. ORCID는 집계 오류를 고쳐도 현재 자료와 과거 기준 정답의 차이가 남는다. Freud의 다른 실행은 탐색을 이어가 정답을 찾았으므로 무조건 빨리 종료하는 규칙도 적절하지 않다.

### 언제 무엇을 보고, 무엇을 반환하는가

Evaluator는 두 시점에 사용한다. 같은 역할을 사용하되 probe 평가와 실행 평가의 지침은 구분한다.

| 시점 | 입력 | 평가할 내용 |
|---|---|---|
| Probe 응답 이후, refiner 이전 | 원 질문, 위임 초안·context, 새 probe 응답 전문, 현재 state, artifact 목록 | 관측과 가정의 구분, 우려의 근거, 수정 필요성, 사전 확인 또는 실행 중 확인할 사항 |
| Worker 실행 이후, 다음 행동 결정 이전 | 원 질문, 실제 전달한 instruction·context, 새 실행 보고 전문, 현재 state, artifact 목록 | 지지되는 결과, 완료 범위, 집계와 포함·제외 기준, 실패한 탐색, 다음 확인의 필요성 |

새 worker 보고는 요약 대신 전문을 제공한다. Probe 응답과 추가 확인 보고도 동일하다. Artifact 목록에는 ID·제목·worker_id·stage를 보여주며, 과거 보고 전문은 필요한 경우에만 ID로 조회한다. 도구 결과 전체는 자동으로 붙이지 않고 근거를 확인할 때 연결된 원문을 조회한다. 도구 결과는 무엇이 반환됐는지를 보여주는 기록이지, worker의 해석까지 입증하는 것은 아니다. 추가 질문·확인 결과가 오면 관련 판단을 다시 평가하되, 새 정보 없이 같은 평가를 반복하지 않는다. Probe를 생략한 위임에는 probe 평가도 없다.

Evaluator는 다음 내용을 반환한다.

- **주장과 근거:** 어떤 관측·해석·결론을 어느 출처·계산이 뒷받침하는가. 가정이나 계획만 있는 경우도 구분한다.
- **진행 상황:** 실행에서 끝낸 작업, 확인하지 못한 항목, 시도한 경로는 무엇인가. Probe의 계획을 완료로 세지 않는다.
- **수정할 판단:** 기존 결과·가정·기준 중 바꿔야 할 것이 있는가. 있다면 근거는 무엇인가.
- **필요한 변경·확인:** 지시문 수정이 필요한가. 어떤 사실을 더 확인하면 답이나 다음 작업이 달라지며, 언제 어떤 자료로 확인할 것인가.

부분합처럼 코드로 검사할 수 있는 것은 harness나 worker가 계산하고 evaluator가 그 결과를 읽는다. 외부 자료를 새로 찾아야 하면 확인할 작업을 제안한다. 다음 작업과 executor, 종료 여부는 orchestrator가 결정한다. Refiner는 평가에서 정한 변경을 instruction·context에 표현하고, 그 과정에서 새 판단이 필요해지면 임의로 확정하지 않고 재검토를 요청한다.

### 원 질문의 기준을 바꾸는 판단

Probe가 제기한 우려는 우선 미확인 가정이나 위험으로 기록한다. 필수 실행 조건으로 채택하려면 원 질문 또는 출처의 어떤 내용이 이를 뒷받침하는지, 왜 그 내용이 추가 조건까지 요구하는지, 기존 해석과 비교해 답의 범위가 어떻게 달라지는지를 설명한다. 원 질문 문구를 인용했다는 이유만으로 승인하지 않는다. arXiv의 “January 2020”은 시점 검토의 근거가 되지만, 그 자체로 항목별 당시 보관 자료를 필수로 요구하는 근거가 되지는 않는다.

해결되지 않은 해석은 실행 중 비교할 대상으로 남길 수 있다. Defer_to_execution은 확인을 실행에 맡기는 결정이며, 확인이 안 되면 답을 보류하라는 자동 조건이 아니다. 가능한 다른 해석이 있다는 것과 자료가 어느 답도 지지하지 못한다는 것을 구분한다. 모든 가정을 증명하거나 모든 대안을 배제하도록 요구하지 않는다.

실행 후 평가도 수정된 instruction의 준수만 확인하지 않고 원 질문과 근거를 기준으로 한다. “확정할 수 없다”는 답뿐 아니라 확정한 수치·이름도 같은 기준으로 검토한다. 원 질문의 기준 변경과 최종 답 채택의 근거는 trace에 남긴다.

### 기대하는 변화와 주의할 점

Probe의 우려가 근거 없이 실행 조건으로 바뀌는 일, 근거 없는 최종 선택, 모순된 집계를 줄이는 것이 목적이다. Refiner의 기존 analysis와 새 evaluator를 중복 호출하지 않는다. 수정할 내용이 없으면 refiner 호출을 생략할 수 있지만, probe에서 얻은 관측과 가정은 그대로 저장하고 필요한 내용을 전달한다.

같은 모델은 같은 오류를 승인할 수 있으며, 평가 호출과 기록 조회의 비용도 늘어난다. 역할 분리는 판단의 독립성을 보장하지 않는다. 새로운 근거가 없으면 기존 결과를 유지할 수 있어야 하며, evaluator가 추가 의심과 증명 요구만 늘리지 않는지도 확인해야 한다.

[십이지 사례](../reports/cases/analysis/853c8244.md)는 항목별 판정과 재확인도 같은 시각 오판을 반복했다. [ScienceDirect 사례](../reports/cases/analysis/0b260a57.md)는 필요한 자료에 접근하지 못했다. 이런 실패는 evaluator나 목록만 추가한다고 해결되지 않는다. 평가가 유효한 후보를 잘못 배제하거나 호출 비용만 늘리는지도 함께 확인해야 한다.

## 4. 전체 동작과 prompt·trace

```text
Orchestrator: 원 질문과 state를 읽고 작업·executor·context·위임 초안 선택
  → Probe: 위임 초안에 대한 이해·가정·위험·계획 응답
  → Harness: probe 응답·도구 결과를 artifact pool에 저장
  → Evaluator: probe 평가, state 갱신과 지시 수정·확인 필요성 제안
      [기존 결과를 뒤집거나 답 기준을 바꾸는 제안은 orchestrator가 채택 여부 결정]
  → Harness: state와 이력 반영
  → Refiner: 평가에 따라 instruction·context 수정, 필요 없으면 생략
  → Worker: instruction과 선택된 context로 실행
  → Harness: 실행 보고·도구 결과·파일을 artifact pool에 저장
  → Evaluator: 결과·근거 검토, state 갱신 제안
  → Orchestrator: 평가와 변경 제안을 보고 다음 작업 또는 종료 결정
  → Harness: 채택한 state 변경과 결정 이력 반영
```

첫 위임에는 이전 실행 기록이 없으므로 state와 context가 비어 있을 수 있다. 첫 실행의 평가를 반영한 뒤 orchestrator가 남은 작업을 골라 두 번째 위임 초안을 만든다. Refiner가 이전 instruction을 계속 고쳐 다음 작업을 정하는 구조는 아니다. Probe를 생략한 위임은 probe 수집·평가를 건너뛰며, 사전 확인이 필요하면 그 결과를 저장·평가한 뒤 수정으로 진행한다.

각 prompt의 첫 단락은 이번 호출에서 할 일을 직접 설명한다. 규칙과 이번 입력을 구분하고, 모델이 실제로 받는 정보만 참조하게 한다. Worker에게 이전 대화 전체를 알고 있다고 가정하지 않는다. Evaluator는 근거와 판단을 검토하고, refiner는 필요한 변경을 지시문에 반영한다. 같은 checklist를 모든 역할에 반복해서 넣지 않는다.

Trace에는 원본 기록 ID, state 변경 전후와 근거, 실제 전달한 context, evaluator의 의견과 orchestrator의 결정, executor 선택 이유·비용을 연결해 남긴다. 사람이 읽을 때도 “어떤 정보를 보고 이 작업을 맡겼고, 결과를 왜 채택하거나 바꿨는가”를 확인할 수 있어야 한다. 기준 정답과 사후 채점은 모델에게 주는 기록과 분리한다.

검색 비용은 prompt에만 맡기지 않는다. 도구 코드가 task별 검색 사용량과 상한을 관리하고, 남은 예산을 다음 행동 결정에 제공한다. 기록과 evaluator가 불필요한 재시도를 줄일 수는 있지만 비용 상한을 보장하지는 않는다.

## 5. 실험과 구현 범위

먼저 현재 시스템과 통합 구성을 같은 문제에서 처음부터 반복 실행해 비교한다. 작업 선택과 executor까지 바뀌므로 첫 위임 checkpoint만 비교하는 것으로는 전체 효과를 보기 어렵다. 비교할 기존 refiner 설정, 후보 모델, prompt, 비용·시간 상한과 반복 수는 실행 전에 정한다.

정답률과 모든 호출을 포함한 비용·시간을 우선 보고한다. Trace에서는 전달 누락, 중복·미완료 집계, 가정이 실행 기준으로 채택된 근거, 반복 탐색에서 달라진 점, 평가 후 실제로 얻은 새 정보를 확인한다. 기존 탐색 집합의 결과를 새로운 문제에 대한 성능으로 주장하지 않고, `eval_v1`은 최종 평가 전 열람·튜닝·실행하지 않는다.

그다음 probe 평가와 실행 후 평가 각각의 제외, executor 고정, 실제 probe 제외, state 대신 기존 context 전달 등의 ablation을 필요한 순서로 수행한다. Probe 평가를 제외할 때 기존 analysis를 복원할지 단순히 평가를 생략할지도 명시한다. 기록 방식을 비교할 때 필요한 정보까지 없애지 않도록 한다. 첫 통합 비교는 전체 구성의 효과를 보는 것이며, 개별 기능의 효과를 분리해서 주장하지 않는다.

초기 구현은 artifact pool·ID 조회, 탐색 이력을 포함한 state 갱신, context 선택·전달, probe·실행 evaluator, 수정에 집중한 refiner, executor 선택과 검색 예산 관리에 한정한다. 별도 delegator나 기록 관리용 agent, vector DB는 추가하지 않는다. 기록의 기본 항목은 위 구성을 사용한다. 세부 저장·조회 방식, 모델과 예산, probe 적용 기준은 구현 전에 정한다. 현재 코드를 설명하는 [framework](../framework.md)와 이 설계안은 구분하고, 도입할 때 구현 문서·버전·결정 기록을 함께 갱신한다.

- [논문 prompt 작성 분석](../thinking-before-thinking-prompt-writing.ko.md), [prompt engineering 분석](../thinking-before-thinking-prompt-engineering.ko.md): 역할별 작업, 입력 범위, 근거와 판단 규칙을 명확히 쓰는 방법.
- [기존 연구 설계](../../../pilot/docs/design/2026-10-05-GAIA-Probe-Query-Pilot-Study.md): 실행 모델을 고정하고 위임 전 지시문 개선을 비교했던 이유.

OpenCV, Ruffwear, arXiv, ORCID, Freud의 위 경로는 보존된 실행 기록과 대조했다. 원본 위치는 [probe 비교 manifest](../../outputs/experiments/2026-10-09_probe-condition-comparison/manifest.json)에서 task ID와 condition으로 찾을 수 있다. 모든 도구 원문을 다시 전수 판독한 것은 아니다.

v10/r12의 새 사례는 [base 실행](../../outputs/experiments/2026-10-11_v10-r12-check/base/runs/)과 [probe 조건 실행](../../outputs/experiments/2026-10-11_v10-r12-check/restore/runs/)의 해당 task 기록을 근거로 한다. 새 사례를 과거 보고서의 동일 task 결과와 구분하며, 사후에 확인한 정답과 탐색 경로는 실행 prompt에 주입하지 않는다.


## 구현된 초기 범위 (2026-10-11 KST)

현재 동작 계약은 [framework](../framework.md), CLI·비교 조건과 검증은 [실험 안내](../experiments.md)를 기준으로 한다.
두 조건은 `direct_execution`과 `multi_worker_probe`다. Probe 조건은 모든 등록 worker를 매 위임 한 번씩
독립 호출하며 최대 도구 3회다. Direct 조건에는 실행 후 evaluator가 공통으로 있다.
Orchestrator·evaluator·refiner는 별도 prompt/call의 `luna-high`다. 고정 role→executor 매핑은 제거했다.

원본은 run-local artifact ID로 저장·조회하며 제목 누락과 실패도 보존한다. State는 evaluator의 전체 교체
제안을 orchestrator가 채택/거부한 뒤 반영한다. 행 선택은 입력 snapshot의 0-based 번호다. Controller 조회는
JSON `read_memory` 행동으로 최대 3라운드이며 원본 기록 읽기만 제공한다. Refiner는 수정 표현만 수행한다.
도구 원문은 보고에 연결해 조회한다. 별도 context 저장소·state ID·관계 graph는 없다.

위임 초안 이후/probe 이전 format 2 checkpoint가 artifact·state·context 선택·누적 budget/credit을 포함한다.
과거 checkpoint와 옵션은 새 의미로 재사용하지 않는다. 유료 검색은 실제 Serper 요청 지점에서 task당
100-credit 상한을 적용하며 probe/실행/재시도와 복원에 걸쳐 유지한다. Cache와 무료 fallback은 허용한다.
예산 소진 시 처리와 알려진 비용/과금 불명 구분은 framework에 명시했다.

오프라인 계약 검사만 수행했다. 전체 구성의 fresh 비교는 별도 실험 계획을 확정한 뒤 진행하며, 반복 수·
총 지출·조건 순서를 실행 전에 고정한다. 이번 구현에서는 유료 실험을 하지 않았고 `eval_v1`은 열람하지 않았다.
